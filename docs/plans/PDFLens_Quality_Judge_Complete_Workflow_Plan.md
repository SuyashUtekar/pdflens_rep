# PDFLens Quality Judge --- Complete Implementation Plan

**Application:** PDFLens Quality Judge\
**Purpose:** On-premises quality evaluation of PDFLens PDF processing
outputs\
**Modules:**\
1. Conversion Quality Evaluation (page-wise PDF-to-DOCX evaluation)\
2. Metadata Quality Evaluation (PDF-to-metadata JSON/assets evaluation)

**Document status:** Proposed implementation baseline\
**Version:** 1.0

------------------------------------------------------------------------

## 1. Executive Summary

The PDFLens Quality Judge is an independent evaluation application that
measures the quality of outputs produced by PDFLens. It uses the
original PDF as the reference source and evaluates two distinct output
contracts:

-   **Conversion output:** The DOCX generated from the original PDF.
-   **Metadata output:** The metadata JSON and associated image/table
    assets generated by PDFLens.

The application contains two evaluation modules that share
infrastructure but maintain separate criteria, evidence, scores,
reports, and quality gates.

### 1.1 Module A --- Conversion Quality Judge

Evaluates the converted DOCX against the original PDF **page by page**.
It checks content preservation, document structure, tables, images,
reading order, and visual/layout fidelity.

The module must support non-one-to-one pagination. A PDF page may
correspond to multiple DOCX pages, multiple PDF pages may flow into one
DOCX page, or a page may need region-based alignment. The implementation
must not assume PDF page N always corresponds to DOCX page N.

### 1.2 Module B --- Metadata Quality Judge

Evaluates the metadata JSON and related assets against the original PDF
and the extraction configuration used for that PDFLens run. It checks
page-wise metadata completeness and correctness, headers, footers,
footnotes, hyperlinks, image metadata, table metadata, page
associations, asset references, and schema consistency.

### 1.3 Key design principles

1.  Use the original PDF as the ground-truth reference.
2.  Keep conversion and metadata evaluations logically independent.
3.  Use deterministic checks wherever exact comparison is possible.
4.  Use an on-prem multimodal LLM as a judge for semantic and visual
    decisions that cannot be reliably reduced to exact rules.
5.  Require evidence for every FAIL and INCONCLUSIVE result.
6.  Evaluate at page or element level first, then aggregate to document
    level.
7.  Distinguish `N/A`, `NOT_REQUESTED`, and `INCONCLUSIVE`.
8.  Preserve traceability from every finding to a PDF page, DOCX
    page/region, JSON path, or asset.
9.  Do not treat the judge's LLM output as ground truth; validate its
    structured response and calibrate it against human-reviewed
    examples.
10. Keep all documents, extracted evidence, model calls, and reports
    within approved organizational infrastructure.

## 2. Scope

### 2.1 In scope

-   PDF and PDFLens output ingestion.
-   Input artifact and extraction-configuration validation.
-   PDF page rendering and content extraction.
-   DOCX text, structure, table, and image extraction.
-   DOCX rendering for visual comparison, using an approved renderer.
-   PDF-to-DOCX page/region alignment.
-   Page-wise conversion evaluation.
-   Metadata JSON parsing and schema validation.
-   Page-wise and element-wise metadata evaluation.
-   Image/table asset validation.
-   Deterministic and LLM-based evaluation.
-   Scoring, severity classification, quality gates, and reports.
-   Persistence of run metadata, findings, and scores.
-   Evaluation reproducibility, audit logging, and human review.
-   Benchmarking PDFLens versions or alternative PDF processors using
    the same evaluation contract.

### 2.2 Out of scope

-   Replacing PDFLens itself.
-   Modifying or correcting PDFLens outputs automatically.
-   Evaluating downstream chunk quality. That belongs to the separate
    Section-wise Chunk Quality Judge application.
-   Treating the judge as a substitute for human acceptance testing.
-   Assuming every visual object in a PDF must be extracted as an image.
    The extraction contract must define whether vector graphics, logos,
    backgrounds, and decorative elements are in scope.
-   Assuming all metadata fields are expected in every run. The
    extraction configuration determines which fields were requested.

## 5. End-to-End Workflow

### Step 1 --- Create an evaluation run

The client submits the source PDF, PDFLens output artifacts, PDFLens run
information, extraction configuration, and selected modules.

The orchestrator: 1. Validates the request. 2. Creates an evaluation run
ID. 3. Records artifact references and configuration versions. 4.
Schedules selected modules. 5. Tracks module and run status
independently.

Suggested statuses:

-   `RECEIVED`
-   `VALIDATING_INPUTS`
-   `IN_PROGRESS`
-   `PARTIALLY_COMPLETED`
-   `COMPLETED`
-   `FAILED`
-   `REVIEW_REQUIRED`

### Step 2 --- Validate artifacts

Check: - Required artifacts are present. - File types and sizes are
permitted. - ZIP entries do not contain path traversal or unsafe
paths. - Files are readable and not corrupt. - SHA-256 hashes are
calculated. - PDF, DOCX, JSON, and asset references are internally
consistent. - The extraction configuration is available for metadata
evaluation.

If a required artifact is missing, fail only the affected module where
possible. For example, a missing DOCX should not prevent metadata
evaluation if the PDF and metadata JSON are valid.

### Step 3 --- Build source PDF evidence

Create a normalized representation of the original PDF:

-   Document-level properties.
-   Page count and page dimensions.
-   Page images at controlled resolution.
-   Page-wise text and word/line bounding boxes, where available.
-   Paragraph and block candidates.
-   Tables and cell content, where detectable.
-   Images and graphics according to the declared extraction contract.
-   Headers, footers, footnotes, hyperlinks, and page associations where
    identifiable.
-   Evidence IDs linking every extracted element to its page and
    bounding box.

Retain both the raw extractor output and normalized evidence. Extraction
uncertainty must be recorded; it must not silently become a PDFLens
failure.

### Step 4 --- Run selected evaluation modules

Run Conversion and Metadata modules independently. They may execute in
parallel after common evidence preparation.

### Step 5 --- Aggregate and persist

Persist: - Module status. - Criterion-level outcomes. -
Page/element-level findings. - Scores and denominators. - Evidence
references. - Model and prompt versions. - Quality-gate decisions. -
Human-review decisions, if any.

### Step 6 --- Generate reports

Produce: - Conversion report. - Metadata report. - Combined PDFLens
Quality Judge report. - Machine-readable JSON. - Optional human-readable
PDF/HTML report, subject to organizational requirements.

# PART A --- CONVERSION QUALITY EVALUATION

## 6. Conversion Evaluation Objective

The Conversion module evaluates whether the PDFLens-generated DOCX
preserves the meaningful content and structure of the original PDF.

The primary evaluation unit is the **source PDF page**, but the module
must support cross-page and region-level alignment when DOCX pagination
differs.

### 6.1 Inputs

-   Original PDF.
-   Converted DOCX.
-   Optional renderer-produced DOCX PDF.
-   Conversion criteria and evaluation configuration.

### 6.2 Outputs

-   Page alignment map.
-   Page-level criterion outcomes.
-   Page-level scores.
-   Document-level conversion score.
-   Failure list with evidence and severity.
-   Conversion quality-gate result.

------------------------------------------------------------------------

## 7. Page-wise Conversion Workflow

### Step 1 --- Extract original PDF page evidence

For each source page, capture: - Page number and dimensions. - Rendered
page image. - Text blocks, lines, and words. - Bounding boxes. - Heading
and paragraph candidates. - Lists and numbering candidates. - Tables and
cell text, where extractable. - Images and graphics according to the
agreed scope. - Reading order candidates. - Page-level extraction
confidence.

Use a combination of PDF text extraction and rendering. For scanned
PDFs, use an approved OCR engine. Do not assume the PDF text layer is
reliable simply because text extraction returns content.

### Step 2 --- Extract DOCX evidence

Parse the DOCX package to capture: - Paragraph text and style. - Heading
levels. - Lists and numbering. - Tables, rows, columns, and cell text. -
Embedded images and relationships. - Section properties, page size,
margins, and orientation. - Headers and footers where relevant to
conversion. - Explicit page and section breaks.

A DOCX file is a flow-based document and does not inherently preserve
fixed page boundaries. Structural extraction alone cannot provide
reliable rendered page numbers.

### Step 3 --- Render DOCX

Use an approved and version-pinned rendering engine, such as LibreOffice
headless if permitted by the organization, or an internal
document-rendering service.

Capture: - Rendered page images. - Rendered page text and coordinates,
if supported. - Page count. - Page dimensions. - Rendering warnings and
failures.

The renderer is part of the evaluation environment. Record its name and
version because rendering differences can change pagination and layout.

### Step 4 --- Align source PDF pages with DOCX output

Build a page/region alignment map using multiple signals:

1.  Text similarity between PDF and DOCX rendered pages.
2.  Sequence and continuity of extracted text.
3.  Heading and section anchors.
4.  Table and image anchors.
5.  Page-level visual/layout signals.
6.  Explicit page-break information where reliable.

Support these relationships:

-   `ONE_TO_ONE`: one PDF page maps to one DOCX page.
-   `ONE_TO_MANY`: one PDF page maps to multiple DOCX pages.
-   `MANY_TO_ONE`: multiple PDF pages map to one DOCX page.
-   `REGION_TO_REGION`: a source page or region maps to a region in one
    or more DOCX pages.
-   `UNMATCHED`: no sufficiently reliable alignment found.

Alignment confidence must be stored. Low-confidence alignment should
produce `INCONCLUSIVE` or `REVIEW_REQUIRED`, not an automatic conversion
failure.

### Step 5 --- Evaluate each source PDF page

For every PDF page: - Identify its aligned DOCX page(s) or regions. -
Run deterministic comparisons. - Build a compact evidence package. - Ask
the multimodal LLM only the questions that require semantic or visual
judgment. - Validate the model response. - Record each criterion outcome
and supporting evidence.

### Step 6 --- Aggregate page results

Generate: - Per-page score. - Per-category score. - Document-level
category score. - Document-level conversion score. - Critical failure
summary. - Alignment uncertainty summary.

## 9. Conversion Evaluation: Deterministic Checks vs LLM Judge

### 9.1 Deterministic checks

Use code for: - Exact or normalized text comparison. -
Numeric/date/identifier comparison. - Text similarity and sequence
alignment. - Paragraph and heading counts, where comparable. - Table
dimensions and cell text. - Image file presence and dimensions. - Page
dimensions and orientation. - Missing/duplicate content candidates. -
Bounding-box and overlap calculations. - DOCX package integrity. -
Rendering success and page count.

### 9.2 Multimodal LLM checks

Use the on-prem multimodal model for: - Semantic equivalence when
formatting changes are legitimate. - Reading-order judgments in complex
layouts. - Whether a visual difference materially changes meaning. -
Whether a table remains understandable when its layout changes. -
Whether a figure/caption relationship is preserved. - Whether a page is
visually readable despite reflow. - Adjudication of ambiguous
deterministic findings.

### 9.3 Hybrid decision approach

1.  Deterministic layer generates candidate findings and evidence.
2.  Rule-based logic resolves high-confidence exact cases.
3.  LLM receives only the relevant PDF/DOCX page images and aligned
    text/structure evidence.
4.  LLM returns structured criterion outcomes with evidence references.
5.  Output validator checks schema and evidence references.
6.  Scoring engine applies the approved rubric.
7.  Low-confidence or contradictory results become `INCONCLUSIVE` or
    `REVIEW_REQUIRED`.

The LLM must not invent missing content, infer evidence from pages it
was not shown, or claim it inspected a file that was not included in its
input.

## 10. Conversion LLM Judge Prompt --- Proposed Template

The prompt must be versioned and tested. This template is a starting
point, not a final production prompt.

``` text
SYSTEM ROLE
You are an impartial document-conversion quality evaluator.

OBJECTIVE
Evaluate whether the supplied DOCX output faithfully preserves the meaningful
content and structure of the supplied original PDF evidence.

EVALUATION RULES
1. Treat the original PDF evidence as the reference.
2. Evaluate only the assigned source page and its explicitly aligned DOCX
   page(s) or region(s).
3. Do not assume PDF page N corresponds to DOCX page N.
4. Do not penalize harmless formatting differences or legitimate DOCX reflow.
5. Do penalize missing, altered, duplicated, misplaced, or unreadable content
   when it materially affects fidelity or meaning.
6. Distinguish source-extraction uncertainty from conversion failure.
7. Do not infer evidence that is not present in the supplied inputs.
8. Every FAIL must include a concise explanation and evidence reference.
9. If evidence is insufficient or alignment is unreliable, return INCONCLUSIVE.
10. Follow the supplied criterion definitions and severity rubric exactly.

OUTCOMES
PASS, FAIL, N/A, INCONCLUSIVE

INPUT
- Evaluation run ID
- Source PDF page number
- Alignment map and confidence
- Applicable criteria
- Original PDF page image and extracted evidence
- Aligned DOCX page image(s) and extracted evidence
- Deterministic comparison results

OUTPUT
Return only valid JSON matching the supplied response schema.
For every criterion include:
- criterion_id
- outcome
- severity (for FAIL only)
- explanation
- evidence references
- confidence
- human_review_required
```

### 10.1 Example structured response

``` json
{
  "source_page": 2,
  "alignment": {
    "type": "ONE_TO_MANY",
    "docx_pages": [2, 3],
    "confidence": 0.93
  },
  "criteria": [
    {
      "criterion_id": "C01",
      "outcome": "PASS",
      "severity": null,
      "explanation": "The meaningful source text is present in the aligned DOCX regions.",
      "evidence_refs": ["pdf:p2:text:block4", "docx:p2:text:block5"],
      "confidence": 0.94,
      "human_review_required": false
    },
    {
      "criterion_id": "T03",
      "outcome": "FAIL",
      "severity": "HIGH",
      "explanation": "A numeric value in the source table differs from the corresponding DOCX cell.",
      "evidence_refs": ["pdf:p2:table1:r3c2", "docx:p3:table1:r3c2"],
      "confidence": 0.98,
      "human_review_required": true
    }
  ]
}
```

The application must validate this output using Pydantic or an
equivalent schema validator. The LLM response must never be used
directly as executable code or trusted database input.

# PART B --- METADATA QUALITY EVALUATION

## 11. Metadata Evaluation Objective

The Metadata module evaluates whether PDFLens correctly extracts and
represents the requested metadata from the original PDF.

It must use: - Original PDF. - Metadata JSON. - Actual extraction
configuration for the PDFLens run. - Actual metadata schema/version. -
Associated image/table assets and references, when available.

The extraction configuration is essential. A field that was not
requested must not be scored as a missing extraction.

### 11.1 Inputs

-   Original PDF.
-   Metadata JSON.
-   Extraction configuration.
-   Metadata schema/version.
-   Image and table assets, if generated.
-   Optional DOCX for cross-checking, but DOCX must not replace the PDF
    as the metadata ground truth.

### 11.2 Outputs

-   JSON/schema validation results.
-   Page-level metadata outcomes.
-   Element-level findings.
-   Field/category scores.
-   Document-level metadata score.
-   Metadata quality-gate result.

------------------------------------------------------------------------

## 12. Metadata Evaluation Workflow

### Step 1 --- Parse extraction configuration

Determine which fields were requested: - Headers. - Footers. -
Footnotes. - Hyperlinks. - Images. - Tables. - Other fields supported by
the actual PDFLens contract.

Represent each field's requested status explicitly.

### Step 2 --- Validate metadata JSON

Check: - Valid JSON syntax. - Expected top-level structure. - Required
keys. - Correct data types. - Valid page numbering. - Valid arrays and
objects. - Valid asset references. - No malformed or duplicate
identifiers where uniqueness is required. - Schema version
compatibility.

### Step 3 --- Build PDF reference evidence

For every page, identify expected metadata candidates: - Header and
footer regions. - Footnote candidates. - Hyperlinks and their visible
text/targets. - In-scope images and their page positions. - In-scope
tables and their page positions. - Page-wise body text and other
declared fields.

Use deterministic extraction and visual/OCR support as appropriate.
Record confidence and known limitations.

### Step 4 --- Match PDF evidence with metadata JSON

Use: - Page number. - Text similarity. - Bounding boxes or
coordinates. - URL/target matching. - Image fingerprints or dimensions
where appropriate. - Table text/structure similarity. - Stable element
IDs where provided by PDFLens.

A match must include confidence and evidence references. Avoid matching
solely by array order.

### Step 5 --- Evaluate requested metadata fields

For every page and applicable field: - Determine whether the field was
requested. - Determine whether the source PDF contains an in-scope
instance. - Match the PDF evidence to the JSON element. - Verify
content, type, page association, and location where available. -
Validate associated asset existence and integrity. - Ask the LLM only
for ambiguous semantic or visual judgments.

### Step 6 --- Evaluate document-level consistency

Check: - Page coverage. - Duplicate IDs. - Invalid page references. -
Broken asset paths. - Orphaned metadata records. - Inconsistent types. -
Cross-page association errors. - Schema and version consistency.

### 13.8 Metadata applicability states

# PART C --- COMMON SCORING AND QUALITY GATES

## 15. Evaluation Outcome Model

Use a common outcome vocabulary, with metadata-specific `NOT_REQUESTED`.

  -----------------------------------------------------------------------
  Outcome                 Meaning                 Included in score?
  ----------------------- ----------------------- -----------------------
  PASS                    Criterion satisfied     Yes

  FAIL                    Criterion not satisfied Yes

  N/A                     Criterion does not      No
                          apply                   

  NOT_REQUESTED           Metadata field was not  No
                          requested               

  INCONCLUSIVE            Evidence insufficient   No; reported separately
                          or ambiguous            
  -----------------------------------------------------------------------

Do not silently convert INCONCLUSIVE to PASS or N/A.

## 16. Scoring Methodology

For each module, calculate scores from applicable PASS and FAIL outcomes
only.

Let: - `P` = number of PASS outcomes. - `F` = number of FAIL outcomes.

### 16.1 Pass percentage

\[ `\text{Pass Percentage}`{=tex} = `\frac{P}{P+F}`{=tex}
`\times 100`{=tex} \]

### 16.2 Signed score

\[ `\text{Signed Score}`{=tex} = `\frac{P-F}{P+F}`{=tex}
`\times 100`{=tex} \]

### 16.3 Raw score

\[ `\text{Raw Score}`{=tex} = P-F \]

If `P + F = 0`, the score is `null` and the report must state that no
scorable criteria were available.

### 16.4 Example

Suppose a page has: - 8 PASS - 2 FAIL - 3 N/A - 1 INCONCLUSIVE

Then:

-   Applicable criteria = 10.
-   Pass percentage = 80%.
-   Signed score = 60%.
-   Raw score = 6.
-   N/A and INCONCLUSIVE are not included in the denominator.

Always report the numerator and denominator alongside percentages.

## 17. Aggregation Rules

### 17.1 Conversion aggregation

Recommended hierarchy:

1.  Criterion outcome.
2.  Page/category score.
3.  Page score.
4.  Category score across document.
5.  Document-level conversion score.

Use a transparent aggregation method. A simple pooled score is:

\[ `\text{Document Pass Percentage}`{=tex} =
`\frac{\sum P_{\text{page}}}`{=tex}
{`\sum`{=tex}(P\_{`\text{page}`{=tex}}+F\_{`\text{page}`{=tex}})}
`\times 100`{=tex} \]

Also report: - Percentage of pages with one or more FAIL outcomes. -
Number of critical/high-severity failures. - Number of pages requiring
human review. - Alignment coverage and low-confidence alignment count.

Do not calculate a page score when the page has no scorable criteria.

### 17.2 Metadata aggregation

Recommended hierarchy:

1.  Criterion/element outcome.
2.  Page/element-category score.
3.  Field/category score.
4.  Document-level metadata score.

Report the requested-field coverage separately. A metadata score must
not appear artificially high because many fields were `NOT_REQUESTED`.

### 17.3 Do not merge module scores by default

Conversion and Metadata scores must remain separate. They measure
different output contracts and have different denominators and
applicability rules.

An optional combined PDFLens score may be introduced later, but only
after: - Weights are agreed and documented. - Critical failures can
override the aggregate. - Missing modules are not silently treated as
zero or perfect. - The report still exposes both independent module
scores.

Suggested severity levels:

  -----------------------------------------------------------------------
  Severity                Meaning                 Examples
  ----------------------- ----------------------- -----------------------
  CRITICAL                Material loss or        Major missing section,
                          corruption that makes   materially corrupted
                          the output unsafe or    critical values,
                          unusable for its        widespread page loss
                          intended purpose        

  HIGH                    Significant defect      Missing important
                          affecting meaning,      table, wrong numeric
                          retrieval, or           value, incorrect page

  MEDIUM                  Noticeable defect with  Misplaced heading,

                                                  localized layout issue

  LOW                     Minor cosmetic or       Small spacing
                          non-material defect     difference, minor
                                                  alignment deviation

Severity must be tied to impact, not merely to the number of mismatched

## 19. Quality Gates

Thresholds below are **provisional** and must be calibrated using a
representative, human-reviewed PDF benchmark set.

Example initial policy:

  -----------------------------------------------------------------------
  Gate                                Suggested condition
  ----------------------------------- -----------------------------------
  PASS                                Pass percentage meets the approved
                                      threshold, no critical failure, and
                                      review conditions are absent

  FAIL                                Critical failure exists, or score
                                      falls below the minimum approved
                                      threshold

  REVIEW_REQUIRED                     Material INCONCLUSIVE results,
                                      low-confidence alignment,
                                      contradictory evidence, or
                                      borderline score

  NOT_EVALUATED                       No scorable criteria or required
                                      artifacts are unavailable
  -----------------------------------------------------------------------

Potential initial threshold for pilot calibration: - Pass percentage at
or above 95%: candidate PASS, subject to critical-failure override. -
85% to below 95%: REVIEW_REQUIRED. - Below 85%: candidate FAIL.

These values are not universal quality standards. They must be tuned by
document type, business impact, and measured false-pass/false-fail
rates.

### 19.1 Critical-failure override

A critical failure should prevent an overall PASS even if the aggregate
score is high.

### 19.2 Independent module gates

-   Conversion gate is calculated from Conversion Evaluation only.
-   Metadata gate is calculated from Metadata Evaluation only.
-   Application-level status summarizes the two module statuses without
    hiding either result.

## 27. Calibration and Human Review

The judge should be calibrated before being used as an automated release
gate.

Recommended process:

1.  Select representative PDFs.
2.  Have domain reviewers annotate conversion and metadata defects.
3.  Run the automated judge.
4.  Compare judge outcomes with reviewer outcomes.
5.  Investigate false passes and false failures.
6.  Refine criteria, evidence preparation, prompts, and thresholds.
7.  Freeze a benchmark version.
8.  Repeat after material model or pipeline changes.

Human review should be mandatory for: - Low-confidence page alignment. -
Critical or high-severity findings during pilot. - Contradictory
deterministic and LLM results. - Large numbers of inconclusive
findings. - New document types not represented in the benchmark. - Model
output that fails validation repeatedly.

Record reviewer decisions to improve future calibration, subject to
approved governance.

## 28. Security and Governance

PDFs and metadata may contain confidential or regulated information.
Apply organizational controls.

-   Deploy model inference within approved on-prem infrastructure.
-   Do not send documents to public LLM APIs unless explicitly approved.
-   Encrypt artifacts in transit and at rest.
-   Enforce role-based access control.
-   Restrict access to evaluation runs and reports by project/realm.
-   Use short-lived, scoped storage credentials.
-   Validate ZIP entries and prevent path traversal.
-   Scan uploads according to organizational policy.
-   Apply file-size, page-count, and decompression limits.
-   Protect against malformed document/parser vulnerabilities.
-   Treat document text as untrusted input; it may contain
    prompt-injection-like instructions.
-   Keep document content separate from system instructions.
-   Do not allow document content to change judge rules or trigger
    tools.
-   Log model, prompt, criteria, schema, and renderer versions.
-   Apply retention and deletion policies to source files, extracted
    evidence, and reports.
-   Avoid logging full document contents unless specifically approved.
-   Maintain audit trails for automated findings and human overrides.

## 29. Performance and Scalability

### 29.1 Processing model

Use asynchronous processing for large documents. A run can be decomposed
into page-level tasks after common extraction and alignment.

### 29.2 Parallelism

Potential parallel tasks: - PDF page rendering. - Page evidence
extraction. - DOCX page rendering. - Independent page evaluations. -
Metadata element matching by page.

Control concurrency based on: - CPU and memory. - Renderer capacity. -
GPU/model throughput. - Storage bandwidth. - Document page count.

### 29.3 Efficiency measures

-   Cache page renders and normalized evidence using artifact hashes and
    versioned extraction settings.
-   Avoid sending full documents to the LLM.
-   Send compact page/region evidence.
-   Batch model requests only when the model and evaluation design
    support it without reducing traceability.
-   Use deterministic checks before LLM calls to reduce inference
    volume.
-   Retry transient failures with bounded exponential backoff.
-   Make tasks idempotent.
-   Store intermediate outputs to resume failed runs.

### 29.4 Reproducibility

Every report must identify: - Source artifact hashes. - PDFLens
run/version. - Judge application version. - Criteria version. - Prompt
version. - Model name/version. - Inference configuration. - PDF/DOCX
extraction library versions. - DOCX renderer and version. - Scoring and
threshold configuration.

## 34. Final Recommended Architecture

Build **one PDFLens Quality Judge application** with two independent
modules:

### Module A --- Conversion Quality Evaluation

-   Page-wise PDF-to-DOCX comparison.
-   Page/region alignment.
-   Content, structure, table, image, and layout evaluation.
-   Page-level and document-level conversion reports.

### Module B --- Metadata Quality Evaluation

-   PDF-to-metadata JSON/assets comparison.
-   Extraction-configuration-aware validation.
-   Page-wise metadata and element-level matching.
-   Schema, consistency, and asset validation.
-   Page-level and document-level metadata reports.

Both modules reuse: - Artifact ingestion. - PDF evidence extraction. -
LLM adapter. - Evidence management. - Scoring framework. -
Persistence. - Reporting. - Security and observability.

Keep module criteria, prompts, scores, and quality gates independent. Do
not merge their scores by default.

The **Section-wise Chunk Quality Judge remains a separate application**
and is not included in this implementation scope.
